## Findings

**IN-1. The pinned USDA releases are a year behind.** Documentation gap; severity medium; confidence high (the FDC download page, opened today, lists Foundation and Branded CSV releases of 2026-04-30; `foodSource.ts:22,29` pin 2025-04-24). SR Legacy's 2018-04 is correct and final (FAQ: "the final release of this data type and will not be updated"). Impact: a rebuild tonight would publish a year-old Branded snapshot (its median record was already January 2020 at MM-51) and miss a year of Foundation additions. Remediation: bump the two URLs to `FoodData_Central_foundation_food_csv_2026-04-30.zip` (3.7 MB zip, 32 MB unzipped per the page) and `FoodData_Central_branded_food_csv_2026-04-30.zip` (428 MB zip, 2.9 GB). Acceptance: `provenance.json` and the pack header name the 2026-04-30 releases. Verification: documentation only; the URLs' form (`https://fdc.nal.usda.gov/fdc-datasets/<file>`) follows the existing pattern and must be confirmed by `mm food fetch`.

**IN-2. USDA Branded can give the grade at most four of the ten micronutrients for most products, so MM-380's "at least five stated" will seldom be met by a barcode food.** Evidence-supported domain concern; severity high for the grade's reach on the barcode pack (456k of 464k foods); confidence medium. Evidence: the GBFPD documentation (opened) says values are "calculated … per 100 grams from those values provided per serving, which are taken from the Nutrition Facts Panel", that submission is voluntary with "certain mandatory information" agreed by the partners, and (Branded documentation, via the search extract) that "when label rounding results in a reported nutrient value of zero, the value on the 100 g … basis will also be zero". The US Nutrition Facts panel since the 2020 update requires vitamin D, calcium, iron and potassium and makes vitamins A and C voluntary; magnesium, zinc, B12 and folate are voluntary (this is the FDA labelling rule as I know it; the FDA page was **not opened** this session and should be cited by the micronutrients role). Consequences: (a) a post-2020 record states four of the ten; (b) a pre-2020 record (the median per MM-51) states calcium, iron, vitamin C and vitamin A in IU, which `extract.sql` rightly refuses (MM-307), so three; (c) a label "0" becomes a stated zero, not unknown, which the grade will count as 0% DV, correct for the label but not for analysis. Expected versus observed: the draft assumes micros "when stated" is a refinement that will often apply; on the barcode pack it will apply mainly to products whose makers volunteer more. Remediation (for the micronutrients and nutrition roles, owner decides): either lower the minimum for `label`-tier foods to the four mandatory, or keep five and say in `docs/food-grades.md` that barcode foods are graded without the micro component in most cases. Measurable only by the build: `coverage.txt` per source (IN-5) will give the real shares. Verification status: documentation plus inspection; shares unmeasured.

**IN-3. A new source falls into the Open Food Facts trust tier and wording.** Reproducible-by-inspection design gap; severity high if FNDDS (or any source) is added without a change; confidence high. `packEntryFor.ts:17-18`: `default: return ['checkThis', 'Entered by Open Food Facts contributors…']`. A `usda_fndds` row would be marked crowd-entered with a false sentence. Also `CandidateFood.ts:30` documents the four ids. Remediation: an explicit case per source and a `StateError` for an unknown source id (the pipeline already throws on an impossible state at `:21-26`); FNDDS as `reference` with its own sentence (proposed: "Compiled by USDA from analysed foods and recipes for the national dietary survey."). Acceptance: a `packBuilder` test that an unknown source throws, and one that `usda_fndds` is `reference`. Verification: inspection only.

**IN-4. There is no rule for the same generic food from two sources.** Design gap; severity medium; confidence high. `PackBuilder.ts:70-73,122-137`: every passing generic candidate is written; `ConflictPolicy` is barcode-only. FNDDS and SR Legacy describe largely the same foods ("Banana, raw" in both), so adding FNDDS doubles many search hits, and `preparationLinks` (`:127`) pairs raw/cooked by name across sources. Today it is harmless (Foundation and SR Legacy overlap on 344 foods and nobody complained; the source name shows in the tier reason). Remediation needs an owner decision (below): keep both and show the source, or a `GenericPrecedencePolicy` on a normalised name that prefers one source and drops the other with a new `DropReason` (`lostDuplicateName`), keeping the report reconciled (`BuildReport.ts:63-65`). Verification: inspection only; the overlap count is a build measurement.

**IN-5. `coverage.txt` cannot answer "how many foods get the full grade".** Documentation gap; severity medium; confidence high. `BuildReport.formatCoverage()` (`:85-93`) is one table over both packs, with no per-source split and no composite rows. Before a pack is published the report should show, **per pack and per source**: foods written; fiber; sodium; fiber and sodium both (the grade's floor); sugars; saturated fat; each of the ten micros; "at least five of ten"; "all ten"; "fully gradeable" (fiber, sodium, sugars, saturated fat and five micros). Add a build-time sanity rule: for `usda_sr_legacy` and `usda_fndds` every one of the thirteen should be stated for well over 90% of written foods; a lower figure means an id or unit slipped in `extract.sql`, since those sources define all thirteen (Sources, S6/S7). Acceptance: the rows exist and `docs/food-grades.md`'s coverage table (`:56-73`) is rewritten from them in the same pull request as the publish. Verification: inspection; the test at `packMicronutrients.test.ts:84-93` covers today's shape and would extend.

**IN-6. USDA's public-domain statement is now confirmed; the pack licence text and MM-51/MM-57 say it was not.** Documentation gap; severity low; confidence high. `https://fdc.nal.usda.gov/` (opened; page says "New for April 2026"): "USDA FoodData Central data are in the public domain and they are not copyrighted. They are published under CC0 1.0 Universal (CC0 1.0). No permission is needed for their use, but we request that users list FoodData Central as the source of the data", with the suggested citation "U.S. Department of Agriculture, Agricultural Research Service, Beltsville Human Nutrition Research Center. FoodData Central. [Internet]. [cited (enter date)]. Available from https://fdc.nal.usda.gov/." Remediation: `packTerms.ts:5-10` can state CC0 1.0 with that citation; MM-51's "License facts" and MM-57's progress note updated; the statement covers FNDDS as an FDC data type. The ODbL share-alike reading for the merged pack still waits for the qualified reader (MM-57 unchanged).

**IN-7. FDC Experimental Foods: reject.** Evidence-supported; confidence high. USDA's own words (Experimental Foods documentation and FAQ, opened): foods "produced, acquired, or studied under unique conditions", which "may or may not be commercially available", and the data "may not be appropriate as a reference for the consumer, diet planning, or dietary guidance". The download page offers no Experimental dataset (only a search link). Not fit for a consumer app; no further work.

**IN-8. Canadian Nutrient File 2026: open and fresh, but not for a US launch.** Assessment; confidence medium. Facts (opened): open.canada.ca record "Canadian Nutrient File, 2026", publisher Health Canada, licence "Open Government Licence - Canada", released 2026-05-19, modified 2026-10-04, resources as CSV (`food_name.csv`, `nutrient_amount.csv`, `nutrient_name.csv`, `cnf_food_group.csv`, `measure_*.csv`, a `cnf_fcen_all-files-data_2026.zip`) with a 2026 users' guide and database-structure PDF; the Health Canada about page says 5,993 foods and "up to 173 nutrients" (the page may still describe the 2015 edition; unclear). Why not now: Canadian fortification rules (milk, flour) differ from US foods, its generic foods descend in large part from USDA SR (my recollection; the users' guide, which states the sources, was not opened), it has no barcodes, it needs a second schema mapping (CNF nutrient codes, not FDC ids), and a third attribution line and licence in the header. Revisit only for a Canadian launch. Other national sets (UK CoFID, Australia's AFCD) are open-licensed but equally unfit for a US launch; not researched further.

**IN-9. The FNDDS CSV's table names and completeness are from recollection, not from a document I could read.** Unverified hypothesis requiring investigation; confidence medium. The FDC "Download Field Descriptions" PDF and the ARS "At A Glance", factsheet and documentation PDFs are encrypted/compressed and could not be read as text; the FDC data-dictionary endpoints returned 400/404. What I expect, to be confirmed by listing the zip: `food.csv` rows with `data_type = 'survey_fndds_food'`; `survey_fndds_food.csv` (`fdc_id, food_code, wweia_category_code, start_date, end_date`); `wweia_food_category.csv`; `food_portion.csv` with `portion_description` and `gram_weight` (FNDDS uses the "undetermined" measure unit the extract already handles at `extract.sql:184`); `input_food.csv` (recipe ingredients). FNDDS values are, as I recall its documentation, complete for all 65 components for every food code (imputed where not analysed). One command settles it: `tar -tf .food_cache/usda_fndds.zip` after fetch, then `head -1` of each CSV.

**IN-10. A category column: every source has one, and a later format can carry it, but MM-380's draft does not need it.** Design/usability improvement; confidence high on the source facts, medium on the product call. Facts: FDC `food.csv` carries `food_category_id` (the data dictionary excerpt via search: "identifies the food category a food belongs to") for Foundation and SR Legacy; FNDDS carries a WWEIA category per food code (FNDDS documentation via search: "a unique 4-digit identification number … each FNDDS food code is linked to a unique category"; FAQ: WWEIA "groups similar foods and beverages together based on usage and nutrient content"); Branded carries `branded_food_category` (provider text; column present in `branded_food.csv`, which the extract already reads whole at `:48-52`); Open Food Facts carries `categories_tags` (data-fields.txt: "the set of normalized tags computer from the categories field"). Interpretation: the per-calorie grade as drafted is category-free by design; a category would serve the fruit/vegetable/legume proxy and drink/oil/nut handling that MM-369's panel wanted (`docs/food-grades.md:29-35,75-78`) and would let FNDDS "as eaten" foods be filtered. Proposal: do not block the format 2 publish on it; a format 3 ticket adds one small app-owned enum (`category`) mapped from the four source taxonomies, plus the raw source category text for tracing; `FoodPackFormat.oldestReadable` keeps older packs opening. Owner and nutrition role decide whether the grade will ever read it.
