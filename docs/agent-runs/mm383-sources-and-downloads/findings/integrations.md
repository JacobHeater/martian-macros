## Findings

**IN-11. Bumping the pins does nothing on a machine with a cache, and `provenance.json` then misstates both the version and the download date.** Reproducible implementation defect (by inspection); severity **high** for the publish (the header would name 2026-04-30 over 2025-04-24 data); confidence high. `food.ts:19-21` reuses `usda_branded.zip` because the file name has no version; `:32` skips the unzip because `usda_branded/` exists; `:41` writes "(downloaded <today>)" for a reused file. On the owner's machine, which fetched on 2026-10-09, `mm food fetch` after IN-1's edit prints "reusing" and builds the old data under the new description. Remediation: put the version in `fileName` (`usda_branded_2026-04-30.zip`, unzip folder keyed the same, or a marker file holding the URL beside the folder, refetched when it differs), and record the real download date per file. Per AGENTS.md this gets a `BUG.*` ticket and a test in `tool/test/` that fails today: a changed URL with a stale file present must download, and a reused file must not be labelled as downloaded today. Until fixed, the command list below starts with deleting the stale entries by hand. Acceptance: `provenance.json` names a release only if that release's bytes are in the cache.

**IN-12. A source that matches nothing vanishes from the report instead of failing the build; this is the one gate that should fail.** Documentation/requirement gap; severity medium; confidence high. The draft says "the first build confirms them (IN-9)" and "the build does not fail on a share; the owner reads the file". If `data_type = 'survey_fndds_food'` or a file name is wrong, the FNDDS branch yields zero rows, `report.read` never gains the key (`PackBuilder.ts:56`, `BuildReport.ts:69`) and `report.txt` simply has no `usda_fndds` line to read. Remediation: `food.ts` passes the configured ids (`foodSources.map(s => s.id)`) to `food-build.mjs` (`--expect usda_branded,usda_foundation,usda_sr_legacy,usda_fndds,off`); the build exits non-zero when any expected source has `read === 0` or `written === 0`, and `report.txt` lists every expected source, zero included. The share rows (IN-5) stay informational as the draft wants, but a reference source (`usda_foundation`, `usda_sr_legacy`, `usda_fndds`) with any of the thirteen stated for under 90% of its written foods should print a `LOW` marker on that row, since those sources define all thirteen (prior S7) and a low share means an id or unit slipped. Acceptance: a test that a build whose expected source list names a source with no candidates fails naming it.

**IN-13. FNDDS portion rows are shaped differently from Foundation's; the draft's "portions" item needs its own branch.** Unverified hypothesis requiring investigation (from the FDC data dictionary via search extract, S20, and recollection); severity medium (serving descriptions on 5,400 foods); confidence medium. The dictionary extract says: for survey foods the `amount` "is not defined and is instead embedded in the portion description", and `measure_unit_id` 9999 is "assigned for food types that do not use measure". The current `concat_ws` at `extract.sql:182-186` tolerates an empty `amount` and already blanks `undetermined`, so "1 cup" should come through. What I recall and cannot cite: for survey foods FDC puts the FNDDS **portion code** (a number such as `10205`) in `modifier`, and FNDDS carries a "Quantity not specified" portion per food. If so, servings would read "1 cup 10205" and "Quantity not specified". Remediation, cheap and harmless if the hypothesis is wrong: in the FNDDS branch of `portion_all`, pass `modifier` as `NULL` when it is all digits (`regexp_matches(modifier, '^\d+$')`) and drop portions whose description starts with "Quantity not specified". Acceptance: after the first build, the servings of three FNDDS foods read as household measures with no bare numbers; a pipeline test over a synthetic FNDDS-shaped portion row.

**IN-14. The survey CSV zip is forty times its own earlier releases; the `data_type` filter is load-bearing, and the nutrient and portion branches should be narrowed to FNDDS ids. Retired codes need no handling.** Evidence-supported concern (S12 sizes); severity low-medium (build time and memory, not correctness); confidence medium on the cause. 200 MB / 1.6 GB against 4-5 MB / 41-54 MB for 2013-2020 and 3.7 MB JSON for the same release says the 2024-10-31 CSV zip very likely carries more than survey rows (a full `food_nutrient.csv` across types would be about that size). As drafted the third `UNION ALL` branch in `nut_all` (`extract.sql:127-135`) would label every row of that file `usda_fndds` and `GROUP BY` all of them before the join with `fd` discards the rest; `portion_all` likewise. Remediation: keep `WHERE data_type = 'survey_fndds_food'` in `fd` (the id form follows `foundation_food` / `sr_legacy_food` at `:120,125`; recollection, confirmed by the build), and semi-join the FNDDS `food_nutrient.csv` and `food_portion.csv` reads on `fd`'s FNDDS `fdc_id`s. The owner lists the zip before building (commands below). Retired codes: the FDC survey download holds one cycle (S15: a single start and end date, 2021-01-01 to 2023-10-31); codes discontinued between cycles are a separate ARS file (S17) and are simply absent, so no `end_date` filter is needed and the ticket's "retired codes" item can say so. One provenance consequence to record: FNDDS `fdc_id`s are reassigned each cycle, so `source_id` traces a food only within the release the header names; the 8-digit food code is the stable identity and `survey_fndds_food.csv` is the only file that carries it. Not needed for this build (the extract needs only `food.csv`, `food_nutrient.csv`, `food_portion.csv`); worth a column in a later format with the category (IN-10).

**IN-15. The normalised-name policy will seldom fire between FNDDS and SR Legacy, and where it does fire (Foundation against SR Legacy) the higher base may be the sparser record.** Evidence-supported domain concern; severity medium-high for the grade's reach on generic foods; confidence medium (naming styles from recollection; the FNDDS documentation is unreadable, S20). The ticket's own example is synthetic: SR Legacy says "Bananas, raw", FNDDS "Banana, raw"; FNDDS names carry "NFS", "NS as to cooking method", "NS as to fat added in cooking" (S20 confirms "NFS, NS" as FNDDS description vocabulary), which SR Legacy never uses. Exact matches after trim/lower/collapse will be a handful of plain names ("Carrots, raw"); the generic pack will mostly show near-duplicates side by side, ordered by the score, which is acceptable but is not what "one name, one food" promises. Where names **are** identical today is Foundation against SR Legacy (the 344 Foundation foods largely reuse SR Legacy descriptions): base 95 beats 90, the SR Legacy record is dropped, and a Foundation profile is often analysed for fewer of the thirteen than SR Legacy's imputed full profile (my recollection; micronutrients role to confirm). The grade needs fiber and sodium (MM-380) and four of the ten; the policy as drafted can trade a gradeable record for an ungradeable one. Remediation (owner decision D2): precedence first by the grade's floor (a record stating fiber and sodium beats one that does not, whatever its base), then by base, then the deterministic tie rule the ticket lacks: the source listed first in the base table, then the lower `sourceId` by `compareStrings`, so the order-independence invariant at `packBuilder.test.ts:238-255` still holds. Add to `report.txt` a line "duplicate winners stating fewer of the thirteen than their loser: N" so the trade is measured, not guessed. The policy must run before `preparationLinks(generic.map(...))` (`PackBuilder.ts:127`) so a dropped duplicate is never a `pairIndex` target; `lostDuplicateName` joins `DropReason.values` (`DropReason.ts:1-14`). `preparationLinks` is otherwise unaffected: FNDDS cooked names carry extra tokens, so their `base` rarely equals an SR Legacy raw's, and cross-source raw/cooked pairs already exist today.

**IN-16. The score says Branded 65 over Open Food Facts 40, but the build's own conflict policy hands every shared barcode to Open Food Facts; the draft's scan rule cannot correct that because there is one barcode pack.** Evidence-supported domain concern; severity **high** (it is the owner's explicit "ranking of barcode scanning on source reliability" and as drafted it changes nothing); confidence high on the mechanics, medium on which way to resolve. `food-build.mjs:28` (`MostRecentPolicy`, tie to `off`), MM-51: OFF's record was newer in all 7,346 both-consistent disagreements, OFF won all 33,736 shared barcodes. `byBarcode` asks packs in turn (`FoodCatalog.ts:40-46`); only `barcode_us` has barcodes; the "two packs, one OFF one Branded" scenario is unreachable with the published packs. So after this story a scan returns a 40 where a 65 was read and dropped as `lostConflict`. Both positions have evidence: freshness (MM-51, median Branded date January 2020, reformulations happen) against self-consistency (MM-51: where only one record passes the checks it is USDA's 2,126 times to OFF's 456) and provenance (the maker's own submission through GS1 against a transcription). The fifty-package hand check that would settle it was never done (HANDOFF line 288). Remediation (owner decision D1): either a `ReliabilityPolicy` for the build (`--prefer reliability`: higher base wins, disagreement still marks "check this", recency only within a source), which makes "a scan takes the most reliable record" true in the one pack that matters; or keep recency and write in the register's "How are foods ranked?" row that the pipeline's barcode choice is by recency and the score orders what survived. The scan rule across packs can stay as drafted for a future second barcode pack; its acceptance scenario should say it is for that case.

**IN-17. The −15 has no carrier in the pack but a sentence.** Documentation/design gap; severity low-medium; confidence high. The format stores `tier` (0-2) and `tier_reason` text; Open Food Facts is `checkThis` on its own (`packEntryFor.ts:17`), so the score cannot key on the tier and must recognise the disagreement sentence at `PackBuilder.ts:15`. Remediation now: move that sentence to its own exported constant (one declaration per file) used by `PackBuilder` and `SourceReliability`, with a test that the two agree; later: a `flags` column in format 3 (with IN-10's category). Note for the register: the mark says two sources disagreed, not which was wrong.

**IN-18. The bases and modifiers are defensible as an ordinal provenance statement; three "Why" cells overstate, and the evidence rows should say what the modifiers do and do not reward.** Assessment (judgement rows, as the owner fixed); confidence high on the sources, medium on the figures, which are the author's. What each row should say:
- *Foundation 95*: "based on analytically derived values", sample-level, current (S14; releases twice a year, S12). Caveat to record: a Foundation profile may be analysed for fewer nutrients than SR Legacy's full profile (IN-15).
- *SR Legacy 90*: "derived from analyses, calculations, and published literature", final April 2018 (S14, S12). The draft's "curated compilation" should become "analyses, calculations and published literature": part of it is imputed.
- *FNDDS 80*: "compiled based on values from FDC data types" (S14), by recipe with Agriculture Handbook 102 yields and Release 6 retention factors (S17), from an FDC extract of October 2023 and, per the documentation's own ingredient file, "other sources" (S20). The draft's "calculated from the two above" should say "mainly from Foundation and SR Legacy, by recipe, with some ingredient values from other sources". One step removed from measurement, hence below both; for a single-ingredient code the number is SR Legacy's own and the 10-point gap is a statement about derivation, not accuracy; say so.
- *Branded 65*: the maker's declaration, submitted through the GS1 data pool (prior S6), per 100 g back-computed from the label serving, within (g)(4)'s 80% floor and (g)(5)'s 20% ceiling (S18), rounded per (c), median record date January 2020 (MM-51). "As rounded and tolerated by 21 CFR 101.9" is right; add "submitted, not verified, by USDA" and the age.
- *Open Food Facts 40*: label data entered by volunteers and, for some products, by producers, without systematic verification (MM-153 context; OFF data page, prior S9); where the two sources disagree and only one is self-consistent, it is OFF's record 456 times to USDA's 2,126 (MM-51 §3). Optional refinement, unverified: the export's `creator`/data-source fields could lift producer-supplied records; I did not confirm the column is in the CSV export.
- *Other by tier 85/60/35*: the fixture pack (`FixturePack.ts:57-59`) and a future source; fine, and it puts the fixture below SR Legacy so stories order as today.
- *−15*: `PreferredSourcePolicy.differ` (10% or 10 kcal / 1 g, `PreferredSourcePolicy.ts:5-10,31-35`), MM-51 §3 (27% of shared, complete products disagree). A Branded record at 50 still ranks above a clean OFF at 40, so the penalty never inverts the source order; it orders within a source.
- *+3 / +2*: these reward **completeness, not accuracy**: a fuller transcription is more likely a careful one, and fiber and sodium are what the grade requires (MM-380). With base gaps of at least 10 and modifiers summing to 5, they can never reorder across sources; they decide only within one source, chiefly Open Food Facts and Branded, where fiber is stated for about 85% and sodium 99% (`docs/food-grades.md:124`). The clamp never binds (range 25 to 100). Say all of that in the row so nobody reads the score as a measurement.
The scenario arithmetic in the ticket is right: 95+3 = 98; 65−15+3+2 = 55; 40.

**IN-20. Source ids now live in four switches.** Design improvement; severity low. `packEntryFor.ts:10-18`, `foodSourceLabel.ts:5-21`, the new `SourceReliability`, `CandidateFood.ts:30`'s comment.
